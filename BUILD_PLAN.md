# Shuttle build plan

Build a domain-organized modular monolith on Bun and Hono. [SPECS.md](SPECS.md) defines behavior and domain boundaries; [IMPLEMENTATION.md](IMPLEMENTATION.md) defines ownership and implementation constraints. This plan defines delivery order. These are planned commits, not completed work.

## Commit sequence

Commit each step only after its completion checks pass. Keep commits independently reviewable and the build green; use injected fakes while a dependency's production adapter is unfinished. A runtime limitation must produce a tested adapter or an explicit specification decision before dependent work continues.

## Working rules

- Keep policy, ports, domain adapters and unit tests with their owning domain. Only `app` uses Hono; only `platform/bun` uses Bun transport APIs; `runtime` constructs and disposes dependencies.
- Update the owning specification section when behavior changes. Keep implementation guidance and acceptance tests in the same commit; do not introduce new production defaults through code alone.
- Run relevant unit/contract checks per commit, network/Redis/browser checks when affected, and the full release suite at commit 13. Tests must assert behavior and resource cleanup.
- Each commit description states the behavior delivered, evidence run and any remaining release blocker. Resolve later defects in focused follow-up commits.
